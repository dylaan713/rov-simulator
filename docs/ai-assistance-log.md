# AI-assistance log

A record of what the AI assistant got wrong or left out, and how each problem was found. It exists to answer one question honestly: where are the real limits of AI-assisted development? It is not a list of things the assistant did well.

M0 was built by five tasks. Each was implemented by a fresh assistant agent working only from a written brief, reviewed by a separate fresh agent that had not seen the implementation, then fixed and re-reviewed until clean. A coordinating agent held the plan and made judgement calls. The entries below are the failures that occurred. Entry 7 was found during review of the technical note, after the first six were logged.

| Date | What the assistant produced | What was wrong or missing | How it was caught |
|---|---|---|---|
| 2026-11-07 | An implementation plan whose drag test asserted 50 N at 2 m/s on the reference body, with the working `0.5 * 1000 * 1.0 * 0.05 * 2**2 = 50` in a comment | The correct value is 100 N: `0.5 * 1000 * 1.0 * 0.05 = 25`, and `25 * 2^2 = 100`. The assistant wrote the plan, so the error was its own, and it sat in a comment that showed its working. The working was wrong. Arithmetic is the part that looks most trustworthy, which is why this matters | Twice, independently, and not by a test. The coordinator recomputed the whole reference body in Python while the task ran. At the same time the implementer found its code disagreed with the plan and stopped to ask rather than editing the expected value. Both reached 100 N. A test suite would have been made to pass by weakening the assertion |
| 2026-11-07 | An integrator test suite: nine tests, all passing | Every test used a derivative that ignores time (`dy/dt = -y` and similar). RK4 evaluates slopes at `t`, `t + h/2`, `t + h/2`, `t + h`; with autonomous problems those time arguments are never exercised. A green suite said almost nothing about that part of the algorithm. It would have failed the first time a thruster command varied with time | A review agent reading the tests, not the code. The coordinator then proved the gap by breaking the integrator three ways. `k2` time changed from `t + h/2` to `t`: 9 of 10 tests still passed. `k4` time changed from `t + h` to `t`: 11 of 12 still passed. Weights changed from (1,2,2,1) to (1,2,2,2): 4 tests failed. Fixed with one test, `dy/dt = t^3` over [0, 1], exactly 0.25 under RK4, which fails on both stage-time mutations tried |
| 2026-11-07 | `analytic_heave` computing `z(t)` as `(w_t^2/a0) * log(cosh(a0 t / w_t))` | `cosh` overflows a double above argument 710, so `z` silently became `inf` for t beyond about 320 s on the reference body, in a public function, with a NumPy warning rather than an error. Every existing test ran to 5 s and passed. The bug lived entirely outside the tested range | A review agent reasoning about the function's domain, not its test results. The coordinator confirmed: `log(cosh(720))` returns `inf`; `logaddexp(720, -720) - ln 2` returns 719.3069 and stays finite even at 1e5. The forms agree to 1.8e-15 over the tested range, so no validation number moved |
| 2026-11-07 | A single-step RK4 test with tolerance 1e-7 | RK4's exact local error on that problem is `h^5/120 = 8.33e-8`, inside the tolerance by only 17%. The test would have passed, then failed mysteriously for the first person to change the step size | The coordinator computing the expected error before execution started, not by observing the test pass. Loosened to 2e-7 with the arithmetic recorded in the test comment |
| 2026-11-07 | A correct zero-drag branch in `analytic_heave`, added by the implementer without being asked | With infinite terminal velocity the general `tanh` form evaluates `inf * 0 = NaN`, so the branch returning the constant-acceleration limit (`w = a0 t`, `z = a0 t^2 / 2`) was right. But nothing exercised it, so nothing recorded that it mattered | The implementer disclosed it. The coordinator checked the branch against the limit at t = 0, 1, 2, 3 s and required a test rather than removing the branch or leaving it untested |
| 2026-11-07 | Parameter validation tested only for what it rejects | Nothing pinned that `drag_coefficient = 0.0` is accepted, and the zero-drag test in the next task depends on it. Tightening `< 0` to `<= 0` later would have passed the whole suite and broken the validation | A review agent that had been told what the following task would need |
| 2026-11-07 | A headline validation figure, 4.83e-10, described as the simulator's agreement with the closed form. The error was in the interpretation of a correct number |

## Summary

The assistant's substance was right first time. The RK4 coefficients, the force balance, every sign and both closed forms were correct, and independent hand re-derivation confirmed them. What it repeatedly got wrong was narrower: the arithmetic in its own explanatory comments (entry 1), and the completeness of its own tests (entries 2, 5 and 6), and, once, what its own correct number meant (entry 7). Twice it shipped something whose tests passed while being blind to the thing most likely to break (entries 2 and 3).

None of the seven failures was caught by a test passing or failing. They were caught by independent hand calculation, by deliberately breaking working code to see whether the tests noticed (the 9 of 10 and 11 of 12 passes under a broken integrator are the clearest example), by a reader asking what the function does outside the range anyone tried, and, for entry 7, by a reader asking what a number actually measures.

Entry 7 is a different failure mode from the other six, which concern wrong code or missing tests. There the code, the number and the tests were all correct, and the explanation attached to a correct result was wrong. That is the sharpest evidence in this log: the assistance can be most confidently wrong exactly where it explains its own correct work, and in this case the wrong explanation would have survived into an interview, where "why is your error 4.8e-10?" has a different answer from the one the note gave.

That is the concrete finding so far on the limits of AI-assisted development: the assistance is strong at producing plausible, usually-correct work, and weak at knowing what it has failed to check. Author's conclusion, not part of the recorded findings: a green test suite written by the same assistant that wrote the code is weak evidence; the checks that mattered were independent of it.
